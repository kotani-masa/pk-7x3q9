# 対抗AIの構築と共進化：引き継ぎ文書

## 1. この版の目的と範囲

目的は、固定した **v6ゾロアークAI** に対して、同じ60枚のレックウザ・ドラパルトを以前より勝たせること。相手AIを弱くする変更、デッキ改変、非公開情報の利用は行わない。今回更新したのは共通Controller、両デッキの方策、両デッキの数値パラメータである。

GitHubの取得元は `kotani-masa/pk-7x3q9`、参照コミットは `sim/baselines/v6/manifest.json` の `upstream`。着手時、GitHubのゲーム・AIコードと手元v6は一致していた。対戦エンジン `index.html` はこの版では変更していない。

v6の全AIソースを `sim/baselines/v6/ai/` に保存した。`ai/decks/ai_zoroark.js` がそのコピーとバイト単位で一致することをベンチマーク・テストで検査する。ゾロアークは専用Policyで動作し、今回修正した共通Controllerの判断処理を使わない。

## 2. 基本思想

1. **数値調整の前に、行動を消している実装の欠落を直す。** スコアの微調整では、未定義値によって消えた行動候補や、呼ばれない対象選択処理を救えない。
2. **一枚の価値より、攻撃までの手順を揃える。** 必要色を特定のアタッカーに集める、加速先を選ぶ、サーチで異なる役割を揃える、展開中のロックを維持する。
3. **相手の公開盤面を読めることを先に保証する。** ナイトジョーカーの名前だけを見て打点0と判断すれば、手張り・昇格・被きぜつの評価が崩れる。
4. **同じ相手・同じエンジン・同じ構築で比較する。** 相手と自分を同時更新した勝率から、自分の改善を結論しない。
5. **選別に使った乱数と最終評価の乱数を分ける。** 60試合の当たり候補をそのまま最強と呼ばない。

## 3. 最終採用した変更

| 箇所 | 問題と変更 |
|---|---|
| レックウザのdefaults | コメントに設定値が巻き込まれて未定義になっていた。値を分離し有限性をテスト |
| 共通Controllerのattach | 加速先メソッドがなく候補先頭へ付いていた。合法な対象を手張りと同じ基準で比較。つけかえの行き先も引き継ぐ |
| 行動候補の生成順 | 特性を評価する前に手張り候補を算出し、ホウオウの判断で利用できるようにした |
| シアノ | 1枚取るたびに仮の手札へ追加して再採点し、本体・ファイアロー・供給役を揃える。観測JSONは変えない |
| レックウザの手張り | 育った本体へ雷・炎・無を集中し、次にファイアロー等の攻撃を完成 |
| レックウザの脅威推定 | ナイトジョーカーのコピー先を公開盤面から計算。どく＋くさりもち、タワーも反映 |
| ドラパルト | デッキ固有の方策ファイルはv6と同じものに戻した。候補比較で加速先選択と数値を調整する方式を採用。`smartAttach=1`、`readCopiedThreat=0` が選別結果 |

ドラパルトでは、ロック維持、ハンマーの対コピー評価、モモワロウへの散布優先、アドレナブレインのコンボ、2匹目のマシマシラなども試した。しかし、それらをまとめた版は900000番台で旧327勝/1000に対して292勝/1000へ後退したため不採用とした。

その後、旧処理を維持できる2つの独立スイッチを設けて切り分けた。`smartAttach=0` は従来どおり合法候補の先頭へ加速する。`readCopiedThreat=0` は従来の脅威推定を使う。両方0・旧パラメータでは30試合の勝敗と通常ログが旧版と完全一致した。選別で残ったのは加速先選択を有効にし、コピー脅威推定を従来のままにする候補だった。アドレナブレインの移動先だけを追加する切り分けも確認用300試合で98勝、採用候補は同条件99勝だったため、今回は追加しなかった。

これは「相手の打点を知らない方が本質的に強い」という結論ではない。新しい脅威推定と、既存の昇格・手張り・危険度スコアとの整合が必要であり、妥当そうな知識を追加するだけで勝率向上を保証できないという観測である。

## 4. 実行時の構造

- エンジンは `index.html`。ヘッドレス実行は `sim/lib/headless.js`。
- AIは別のVMコンテキストにあり、エンジンの `P`、`G`、実際の山札順、相手手札にアクセスしない。
- `cpuView` の複製JSONを受け取り、カード定義 `cd` と自分のデッキリストをキャッシュする。
- 通常の意思決定は、進化・展開・特性・サーチ・加速・手張り・にげるの候補へ点数を付ける方式。準備を終えたら使えるワザから選ぶ。
- カードを複数選ぶ処理と、加速先を決める処理も方策の一部である。`decide` だけ直して完成と考えない。
- 今回のベンチマークは `search:false`。以前からある価値モデルを再学習していない。ニューラルネットの自己対戦強化学習を実施した、という意味ではない。
- 今回の自動調整は **有限候補の集団探索＋別乱数による選別**。選ばれたパラメータは `ai/params/params_dragapult.js` と `params_rayquaza.js` に入る。

## 5. 実験設計と再現

全試合で座席を交互にし、先後選択は方策に従う。最大80ターン。引き分け・上限・未完了・例外は勝ちに数えず別集計する。

| 段階 | 乱数seed | 用途 |
|---|---|---|
| 初回の候補選別 | 100000〜100059 | 各デッキ6候補×60試合 |
| 初回の候補確認 | 200000〜200119 | 上位3候補×120試合 |
| 最初の独立評価（以後は調整用へ移行） | 700000〜700999 | 旧新各1,000試合。ドラパルトの差が小さく追加改善を決定 |
| ドラパルトの追加選別 | 110000〜110099 | ハンマー等の追加修正後に6候補×100試合 |
| ドラパルトの追加確認 | 200000〜200199 | 上位3候補×200試合。これは確認・選別用であり最終評価ではない |
| 2回目の独立評価（以後は調整用へ移行） | 800000〜800999 | ドラパルト310勝/1000、レックウザ135勝/1000。ドラパルトの連携をさらに修正 |
| 不採用版の独立評価 | 900000〜900999 | ドラパルトの後退を確認し、その版を不採用 |
| ドラパルトの切り分け | 120000〜120099、確認200000〜200299 | 12候補×100試合、上位3候補×300試合。旧判断を維持する追加3候補も各300試合で比較 |
| 最終の未使用評価 | 1000000〜1001999 | 旧新各2,000試合×2デッキ、計8,000試合 |

700000・800000・900000番台は結果を見て追加修正を決めたため、その数字を最終評価として再利用しない。最終実験はタグ付きの別ファイルに保存する。途中の予備比較には異なるレックウザのパラメータが含まれるため、その数字を合算しない。最終評価の前に初回採用設定へ戻し、初回のファイル指紋との一致を確認した。

レックウザは初回選別で既定値候補を採用した。その改善は主に処理修正と手張り規則による。74/200の追加戦術版も最終採用版ではないため、その値を最終版の成績として扱わない。最終版の成績は1000000番台で判断する。

初回選別は概要と採用パラメータを保存し、ドラパルトの初回パラメータはファイル指紋の一致まで確認した。800000番台は比較要約と旧側の試合データを保存している。追加選別と最終評価は各試合の結果を保存している。以下のtrainは現在の方策を再調整するコマンドで、過去の選別値と完全一致することを保証しない。

```bash
# AIの動作・情報制限を検査
node sim/run.js test
node sim/run.js verify-info
node sim/run.js verify-hidden

# 以下のtrainは現在のパラメータファイルを上書きする。再調整する場合に実行。
node sim/run.js rivals train --only dragapult --ablate --tag drag3 --pop 12 --games 100 --validation 300 --seed 120000

# 固定した旧AIの比較用成績を生成
node sim/run.js rivals baseline --games 2000 --tag final1m --seed 1000000

# 新AIを比較。エンジン・baseline指紋・seed・試合数が一致する旧成績は再利用する
node sim/run.js rivals eval --games 2000 --tag final1m --seed 1000000
```

- `sim/results/rivals_training_drag3.json`：追加選別の全候補のパラメータ、各試合のseed・座席・勝敗、選別成績、採用番号。初回レックウザの採用情報は `rivals_rayquaza_selection.json`。
- `sim/results/rivals_baseline_round1.json` と `rivals_baseline_800000.json`：過去の旧AI評価。最終比較の旧側の全試合は `rivals_holdout_final1m.json` の各 `baseline` に入る。
- `sim/results/rivals_holdout_final1m.json`：旧新の比較、Wilson 95%区間、勝敗が改善・悪化したペア数、両側の正確二項検定。
- 同一seed・座席のペアで比較するが、途中の行動が変われば乱数の消費も変わる。後続の山札順まで一致する保証はない。
- 個別試合の再現には `node sim/run.js record dragapult zoroark SEED --out sample.pokeca.json` のように完全ログを取得する。大きな生ログは通常配布に含めない。

最終結果はこの文書の末尾と `docs/ai_handoff.json` を参照。

## 6. 相互強化を続ける手順

今回の固定相手に対する強化は、リーグの最初の1世代と位置づける。

1. 採用AIのソース・パラメータ・エンジン・構築・成績を保存し、変更しない。
2. 次は今回のレックウザ・ドラパルトを固定して、ゾロアーク候補を調整する。
3. 最新相手に加え、v6など過去の強い相手とも対戦する。相手の混合比率を記録する。
4. 未使用の評価seedで、相手別成績と全対戦表を確認する。最新相手にだけ勝てる候補や、古い相手へ大きく退化した候補の採用を慎重にする。
5. 採用したら次世代の固定相手にする。前世代の基準を後から書き換えない。

この方式で反復改善は狙える。ただし、相性による循環、特定構築への過適応、方策表現の限界があるため、無限に単調に強くなる保証はない。古いチャンピオンを含む複数相手のリーグが必要になる。

## 7. 次の担当AIへの注意事項

- まず `docs/ai_handoff.json` と3つの結果JSONを読み、ファイル指紋を確認する。
- `sim/baselines/v6/ai/` は実験の比較対象。既知の不具合を意図的に残してあるため、そこを修正しない。
- `sim/training/optimize.js` は以前の共進化用ツールで、ドラパルト・レックウザのfitnessに今回の固定ゾロアークを含めない。今回の再現には `rivals` を使う。
- ドラパルトの同梱構築はクラッシュハンマー型で、ヨマワル・ヨノワールを含まない。方策にボム処理があっても、今回それで勝ったと説明してはいけない。ユーザーの別構築ログと区別する。
- レックウザの盤面エネルギー評価・ランダム打点・退避には近似が残る。相手の全応手を読む完全探索ではない。
- 新しい探索や特徴量を追加したら、旧価値モデルの入力寸法・学習相手分布を確認する。今回の結果から価値モデルの精度は主張できない。
- 今回、一般的な人間相手・大会構築全体への強さは測定していない。
- 最終評価のseedを見てさらに調整した場合、そのseedは以後選別用と扱い、新しい未使用seed群で最終評価をやり直す。

## 8. 最終結果と採用判断

相手は固定v6ゾロアーク、構築とエンジンは同一。seed1000000～1001999、旧新各2,000試合、座席交互、先読みなし。

| デッキ | 旧AIの勝ち | 新候補の勝ち | 旧勝率 | 新勝率 | 対応比較p値 |
|---|---:|---:|---:|---:|---:|
| dragapult | 581/2000 | 602/2000 | 29.05% | 30.10% | 0.289809 |
| rayquaza | 226/2000 | 296/2000 | 11.30% | 14.80% | 1.22532e-05 |

全8,000試合で実行エラー・未完了・引き分け・ターン上限はいずれも0件。

**ドラパルトは29.05%→30.10%の小幅な上昇にとどまり、p=0.290なので、統計的に確かな強化は確認できていない。** 選別候補として暫定同梱するが、目標を十分達成したと説明してはいけない。旧AIは凍結フォルダに残してある。レックウザは11.30%→14.80%、対応比較p≈0.0000123で、この固定相手への改善を確認できた。人間相手・別構築での改善へ一般化しない。両デッキを確実に強化するという目標は、ドラパルト側で未達である。

チェックは既存のゾロアーク盤面・実エンジン手順・記録・構成検査と、対抗AIの追加テストをすべて通過。情報監査は111,933呼び出し、山札全確認9,519回で順序漏れ0。隠れた相手情報を入れ替える検査も19件すべて一致した。
