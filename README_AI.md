# ポケカ エミュレータ：CPU AI（デッキタイプ別・外部ファイル方式）

## 構成

```
index.html                 エミュレータ本体（ルール処理＋AIへの橋渡し層。AIのアルゴリズム自体は含まない）
ai/
  ai_core.js               共通基盤（見える情報だけで判断する仕組み・ダメージ計算・脅威推定・選択処理）
  ai_dragapult.js          クラハンドラパ用のプレイアルゴリズム
  ai_rayquaza.js           メガレックウザ用のプレイアルゴリズム
  params_dragapult.js      自己対戦で調整した数値パラメータ（自動生成）
  params_rayquaza.js       同上
  legacy_cpu.js            旧CPU（未対応デッキ用のフォールバック／比較用ベースライン）
sim/                       画面なしで高速に自己対戦・最適化するためのツール（Node.js）
```

`index.html` は `<script src="ai/...">` でAIを読み込みます。**フォルダごと同じ場所に置いてください**（ai/ が無いとCPUは最低限の動きになります）。
CPU戦を始めると、CPUのデッキ内容から**デッキタイプを自動判定**し、対応するAIを呼び出します（未対応デッキは旧CPUで動作）。

## AIが守っている「プレイヤー目線」のルール

AIは盤面オブジェクトを直接見ず、橋渡し層（`cpuView`）が作った**JSONの複製**だけを受け取ります。

| 情報 | AIに渡るか |
|---|---|
| 自分の手札・場・トラッシュ | 渡る |
| 自分の山札・サイドの**中身と順序** | 渡らない。枚数のみ |
| 相手の場・トラッシュ・スタジアム | 渡る（公開領域） |
| 相手の手札・山札・サイドの中身 | 渡らない。枚数のみ |
| 相手のデッキタイプ | 渡る（「ある程度の動きは分かる」前提） |
| 相手のデッキリスト詳細 | 渡らない |

**山札・サイドの推定（信念追跡）**：自分のデッキリストは既知なので、「デッキリスト − 見えている自分のカード（手札・場・付属カード・トラッシュ）」＝「山札＋サイド」を常に計算します。
サーチ等で**山札を初めて全確認した瞬間に、山札の内訳が確定し、サイドの内訳も確定**します（それ以前は、サイドに落ちている確率を枚数比で見積もる）。サイドを取ったときは取ったカードで更新します。
山札を全確認するときの並び順は、AIに渡す前にシャッフルしています（順番は分からない）。

**構造的な保証**：`sim/headless.js` はAIを盤面とは別の空の実行環境（vm）で動かします。AIコードが盤面のグローバル変数（`P`,`G` など）を参照しようとすると、その場でエラーになります。
`node sim/verify_info.js` で「相手情報は公開領域と枚数のみ／山札順が漏れていない」を実際の対戦で検査できます。

## 勝利条件

エミュレータ側（`judge()`）に実装しました。

1. サイドを取り切る
2. 相手が**自分の番の開始時**に山札を引けない（山札0枚になった時点では負けない）
3. 相手の場にポケモンが1匹もいなくなる

同時に満たした場合は、満たした条件の数が多い方が勝ち。同数なら**両者敗北**（`G.win = -1`）。
カースドボムのように「自分がきぜつ→相手のポケモンもきぜつ」が続く処理は、両方が済んでから判定します。
AI側も、山札が少ないときはドローを控える／勝ちになる攻撃・ボスを最優先／場が空になる自滅を避ける、を入れています。

## ルール微調整（エミュレータ側）

- **マリガン**：任意操作ではなく強制。手札にたねポケモンがあれば行えず（ボタン廃止）、なければ自動で強制マリガンし、**手札を全て公開**します（ログ＋公開オーバーレイ）。相手のマリガン回数ぶんの追加ドローは従来どおり。
- **セットアップ**：置いたバトル場・ベンチのポケモンは、相手側の画面では**裏向き**。両者のセット完了（バトルスタート）と同時に一斉に表になります。CPUのセットアップ時には相手盤面の情報を一切渡さないので、後攻の情報アドバンテージはありません。
- **グッズ・サポートの処理順**：使うと手札から離れ、盤面の「使用待機」スロットに置かれます（ターン終了ボタンの下、山札と同じ大きさ。1枚ずつしか出ないので、自分・相手どちらのカードも同じスロット）。ログは中央の表示部から左側へ移しました。CPU・オンライン戦で相手の番のときは、ターン終了ボタンは出さず（「相手の番です」表示）、スロットは相手盤面寄りの上側に出ます。スロットに枠線・背景色は付けていません（盤面と同化）。効果処理が終わってからトラッシュへ。
  ハイパーボールなら **使用（使用待機）→ コスト選択 → コスト2枚がトラッシュへ → 山札サーチ → 効果終了 → ハイパーボールがトラッシュへ**。
  サーチ画面で「保留」して盤面を見ると、ハイパーボールは使用待機・コスト2枚はトラッシュ・手札からは消えた状態です。
  条件を満たさない／コスト支払い前に取り消した場合は手札に戻ります。使用待機のカードはAIにも「見えている自分のカード」として渡ります（山札・サイドの推定が狂わないように）。
- **サーチの公開**：相手（CPU／オンライン）が山札からサーチして手札に加えたカードは、画面中央に**表向きで見せてから**相手の手札へ飛ばします（例：ポケパッドでドロンチ → 「P2が山札から手札に加えました：ドロンチ」）。オンライン対戦でも相手側に同期されます。自分のサーチでは出ません（自分は手札で見えるため）。
  同じ情報はCPUにも渡します（`view.opp.known`＝相手が公開した手札のカードで、まだ手札にあるもの）。現在のAIの判断ではまだ使っていません。
- **相手のモーション**：相手が手札から出したカード（ポケモン・スタジアム・使用待機）、付けたエネルギー・どうぐは、相手の手札の位置から飛んでいきます（これまでは突然現れていました）。山札やトラッシュから出た場合は、その位置から飛びます。
- **CPUの動作速度**：CPU戦中の左側に「速度：ゆっくり／ふつう」ボタン（2段階、設定は保存）。行動と行動の間、対象・カードの選択の間に間を入れています。

## 使い方

```
node sim/verify_info.js                 # 情報制限の検査
node sim/report.js 200                  # 旧CPU／新AI(調整前後) の総当たり比較
node sim/optimize.js --rounds 2 --gens 10 --pop 14 --games 36   # 自己対戦による再調整
node sim/showlog.js dragapult rayquaza 1234 N N                 # 1試合のログを表示（N=新AI, L=旧CPU）
```

### 実際のデッキで再調整する
`sim/decks/*.json` は、公開されている構築を参考に**エミュレータ実装済みカードだけ**で組んだ代表デッキです。
実際のデッキコードの中身と異なる場合は `sim/export_decks.txt` の手順で書き出して `import_decks.js` で取り込み、`optimize.js` で再調整してください。

### 新しいデッキタイプを足す
`ai/ai_xxx.js` を作り、`CPUAI.register('名前', { detect, defaults, space, setup, benchScore, trainerScore, ... })` を書きます（`ai_dragapult.js` が実例）。
`index.html` の `<script>` 行と、`sim/headless.js` の `aiFiles` に追加するだけです。

## 調整の仕組み

`defaults` のパラメータ（評価の閾値・優先度・重み）を、自己対戦の勝率でクロスエントロピー法により最適化しています。
評価は3つの組み合わせ（ドラパ×レックウザ／ドラパ ミラー／レックウザ ミラー）で行い、相手側の最良AIも交互に更新します（共進化）。
旧CPUとの対戦も少し混ぜて、AI同士の循環（じゃんけん状態）に陥らないようにしています。

## エネルギーの扱い（「布石」として考える）
エネルギーは「付けない方がよい」と決め打ちしません。次のように二段構えです。
- **標準AI（先読みなし）**：付け先の系統（今の姿＋進化先）の**どの技でも**、必要エネルギーを埋める（＝その技に近づく）なら加点します。弱い技も含みます（ジェットヘッドの70ダメージも布石）。
  必要数を超える付け方（ネオアッパー等）は小さく減点するだけで、ファントムダイブが撃てるなら付けます。
  どの技にも、進化先の技にも、にげるにも、総数比例の技にも寄与しない付け先だけ、標準AIでは付けません。
- **先読み探索**：エネルギーの付け先を**全て候補**に入れ、その後の展開（次の自分の番まで）で評価して選びます。

`node sim/audit.js` は「必要数を超えて付けた割合」を測る監査ですが、超過が悪いとは限らないので、参考値です。

## 先読み探索（2ターン先まで・相手の手札を仮定）
- **候補**：通常のAIの上位＋エネルギーの付け先（全て）＋技ごとの攻撃＋「攻撃せずに番を終える」。
- **評価**：実際のルール処理で「その行動→（残りは通常のAIで）自分の番→**相手の番**→**自分の次の番**の終わり」まで進め、終了局面を**価値関数**（自己対戦から学習した勝率予測）で採点します。
  段階1＝全候補をこの番の終わりまで（安価）、段階2＝上位候補だけ2ターン先まで（各4回試行）。「今ジェットヘッドで70入れて次に何ができるか」「相手の返しで倒されないか」が評価に入ります。
- **隠れた情報は使いません**：自分の山札・サイドは混ぜ直す。**相手の手札・山札・サイドは、デッキタイプの標準リスト（`ai/ai_refs.js`）−場・トラッシュ・公開済みのカード から仮定して作り直す**（実際の中身は見ない）。
  `node sim/verify_hidden.js`：相手の実際の手札・山札・サイドの並びを入れ替えても、段階2の評価値が変わらない（24/24一致）ことを確認します。
- **価値関数**：自己対戦の約7万局面（36特徴量＋交互作用）からロジスティック回帰で学習（`sim/value_data.js` → `sim/value_train.js` → `ai/value_model.js`）。未知の試合で勝敗をAUC 0.81〜0.86で予測。
- CPU戦の左側の「先読み：ON/OFF」で切り替え（既定ON）。1回の探索は数百ms（ブラウザ・jsdom計測で約200ms）。`ai/value_model.js` / `ai_refs.js` が無い環境では自動的に段階1のみ／無効になります。
- **カードの役割の知識**（ヒューリスティック）：パオジアンは「ただベンチに出す」のではなく、ゼロの大空洞を消せる場面（自分のベンチが6匹以上でダメージを負った高賞金ポケモンを先に捨てて賞金を渡さない／相手に捨てさせる／ジャミングタワーで自分のどうぐが無効）でだけ出して特性を使います。
  ベンチ超過で捨てるポケモンは、ダメージを負った高賞金・狙われているものを優先します。

- **価値関数**：自己対戦の約7万局面（「自分の番の終わりの局面」36特徴量＋交互作用 → その番のプレイヤーが勝ったか）からロジスティック回帰で学習（`sim/value_data.js`, `sim/value_train.js` → `ai/value_model.js`）。

- 追加の思考時間は Node 上で1試合あたり0.3〜0.9秒程度です。

## 評価結果（左側の勝率±95%誤差。代表デッキ sim/decks/、レックウザ側にパオジアン2枚入り）

| 対戦 | 結果 |
|---|---|
| 【旧CPU同士】ドラパ vs レックウザ | 34.0% ±6.6 |
| ドラパ：標準AI（先読みなし） vs 旧CPU（相手がレックウザ／ドラパ、各120試合） | 75.0% ／ 79.2% |
| レックウザ：標準AI（先読みなし） vs 旧CPU（同上） | 69.2% ／ 57.5% |
| ドラパ：**2ターン先読み** vs 旧CPU（同上、34試合） | 85.3% ／ 97.1% |
| レックウザ：**2ターン先読み** vs 旧CPU（同上、60試合） | 68.3% ／ 71.7% |
| 2ターン先読みあり vs 先読みなし（同じデッキ）ドラパ（64試合）／レックウザ（110試合） | **76.6% ±10.4 ／ 68.2% ±8.7** |
| （参考）1ターン先読みあり vs なし（前バージョン、各200試合） | 59.8% ／ 59.0% |

- 先読みを「この番の終わりまで」から「相手の番＋自分の次の番まで」に伸ばしたことで、先読みなしに対する勝率が約+17〜+27%に上がりました（ミラー）。
- 旧CPUに対する勝率は、試合数が少ない（先読みは1試合1〜4秒かかる）ため誤差が大きいです。特にレックウザは旧CPUに対して有意な伸びが確認できていません。
- 価値関数は前バージョンのデッキで学習したままです。レックウザ側のパオジアン追加後に再学習すると、さらに改善する可能性があります。
- 実際のデッキの中身と異なる場合、標準リスト（ai_refs.js）との差が先読みの精度に影響します（`sim/make_refs.js` で再生成できます）。
